# 11 · 五位 AD 键盘（IO10）：OK 键失效的定位与修复

> **现象**：五个键里，四个方向键都正常，**只有 OK 键按下去毫无反应**（OLED 菜单里没法确认/进入）。
> **结论**：不是 UI 问题，也不是"OK 键坏了"——是**驱动把 OK 的 0mV 档当成"没有按键"丢掉了**。
> **状态**：✅ **已实机验证通过**（2026-09-28，COM31，IDF 5.4.0 重新编译烧录）。

## 1. 硬件真相：五档电阻分压（实测）

模块把五个键接到同一根信号线上，靠**不同分压**区分，空闲时被上拉到 VCC：

| 读数（实测） | 对应 | 说明 |
|:---:|---|---|
| **≈0 mV** | **OK** | ★ 直接对地 |
| 615 mV | 丝印 3 | 上 |
| 1380 mV | 丝印 1 | 左 |
| 1968 mV | 丝印 4 | 下 |
| 2638 mV | 丝印 2 | 右 |
| ≈3128 mV | 空闲 | VCC，已到 ADC 量程顶端（饱和） |

**证据**（Claude 调试时留下的串口日志，四个方向键全都在，唯独没有 OK）：

```text
logs/monitor-20260928-205346.log
I (8521)  MAIN: [ADKEY] 1 DOWN (mv=1386)
I (9131)  MAIN: [ADKEY] 2 DOWN (mv=2632)
I (10341) MAIN: [ADKEY] 3 DOWN (mv=615)
I (10681) MAIN: [ADKEY] 4 DOWN (mv=1968)
   ← 按完 1/2/3/4 之后没有任何 OK 事件
```

> 一条独立佐证：在更早的固件上（`BSP_KEY_GPIO_KEY1 = GPIO10` 还是**数字**按键时），
> 按 OK 会打出一条 `[KEY1] click`。数字输入要判低电平才算按下（阈值约 1.5V），
> 说明 **OK 按下时这根线确实被拉到了接近 0V** —— 与"0mV 档"完全吻合。

## 2. 根因：两处代码把 `0mV` 吃掉了

都在 [`adkey.c`](../components/BSP/ADKEY/adkey.c)：

| # | 位置 | 原来的写法 | 后果 |
|:-:|------|-----------|------|
| ① | `adkey_read_mv()` | `if (mv > 0) return mv;` 否则返回空闲值 | `adc_bus_read_mv_avg()` 只在**全部采样失败**时返回 `-1`，**0mV 是合法读数**；写成 `> 0` 就把 OK 的 0mV 当"读失败"，直接替换成空闲电平 |
| ② | `adkey_match()` | 只匹配 4 个方向键（±200mV）+ `[2900, 空闲)` 残余档 | 0mV 离最近的 627mV 档差 600mV，超出容差 → 返回"无按键" |

另外还有一个**误导性的历史结论**（已在新代码注释里标注推翻）：
早期版本把 OK 判定为"比空闲低 5~27mV 的窄带 `[3050,3112]`"，那是**把 ADC 噪声当成了按键信号** ——
那版固件的日志里出现过 `OK DOWN → 30ms 后 OK CLICK` 这种"按下 30 毫秒"的假事件，人身手速不可能这么快。

## 3. 修复内容

### `components/BSP/ADKEY/adkey.c`

1. **`adkey_read_mv()` 判据改为 `mv >= 0`** —— 0mV 是合法读数（OK 对地），只有 `<0` 才算读失败。
2. **新增低压档** `ADKEY_OK_LOW_MAX_MV = 300`：`0~300mV` 一律判为 **OK**（最低的方向键档 ≈615mV，间隔充足）。
3. **保留高压残余档** `[2900, 空闲-3mV)`：兼容"OK 档贴近 VCC"的其它批次模块，两种模块都能用。
4. **新增未匹配告警**：落不进任何档的读数会打一条（10 秒限速）警告，换键盘时一眼就能看到该填什么值。
   ★ 2026-09-29 收窄：只有**低于"最高方向键档 + 容差"**（本机 = 2639+200 = 2839mV）的读数才告警。
   松开手之后空闲线自己抖动（实测 2905~3124mV）也落不进任何档，但那个电压**物理上不可能是任何键**，
   再告警就是纯噪声（10 秒限速都挡不住，实机 28 秒抓包里就冒了一条）。
5. **新增标定日志**：每次松键打印 `标定: 键X 按下期间最低 NNNmV（空闲基线 …）`。
6. **新增 `adkey_last_mv()`**：事件回调里打印**真正触发的那次读数**。

### `components/BSP/ADKEY/adkey.h`

- 更新硬件说明（五档实测值 + 0mV 档的存在），新增 `adkey_last_mv()` 声明。

### `components/BSP/ADKEY/adkey_logic.h`（新增）

- 把"电压 → 哪个键"抽成**纯函数** `adkey_logic_match()`（不依赖 ESP-IDF），
  连**所有调参宏**（容差 / OK 低压档 / 高压档 / 空闲判定线 / 4 个方向键基准值）一起放这里。
- 好处：固件和 PC 端单测读同一份头文件 → 测的就是板上跑的那套阈值，不会"测得跟跑的不一样"。
- 顺手修掉一个测试发现的边界 bug：容差原本是 `diff < tolerance`（实际 ±199mV），
  与文档写的 ±200mV 不符 → 改为含端点 `diff <= tolerance`。

### `main/main.c`

- `[ADKEY]` 事件日志改成打印**触发读数**：
  ```
  I (xxx) MAIN: [ADKEY] OK CLICK (触发读数=0mV, 当前=3128mV)
  ```
  （以前打印实时值，回调跑到时早就松开回到 3128mV 了，所以日志里全是 `mv=3128`，根本没法用来标定。）
- `keyscan` 命令改成**一变就打印**（变化 ≥8mV，50ms 采样），短按也不会漏；
  结束时会打印这段时间的**最低/最高**电压。

### `tools/adkey_test.c` + `tools/run_adkey_test.ps1`（新增）

- PC 端单测与运行脚本，**不用板子**就能验证判键逻辑（详见第 5 节）。

           OK=低压档[0,300]mV 或 高压档[2900,3124)mV, 空闲基线=3128mV, ...

3. **按 OK**，预期看到：
   ```text
   I (xxx) MAIN: [ADKEY] OK DOWN  (触发读数=0mV, 当前=0mV)
   I (xxx) MAIN: [ADKEY] OK CLICK (触发读数=0mV, 当前=3128mV)

   OLED 菜单里按 OK 应该能进入子页 / 执行动作。
4. 想逐个核对电压，敲：

   ```
   然后按 1→2→3→4→OK 各按一下，日志会打印每次变化的电压值。
5. **懒人版：一条命令自动判定** ——

   powershell -ExecutionPolicy Bypass -File tools\verify_adkey.ps1        # 自动挑串口

   它会提示你"5 秒后开始采样，请依次按 1→2→3→4→OK"，然后抓 45 秒串口，
   自动解析出每个键的事件次数与触发读数，并给 PASS/FAIL 结论：

   ```text

     1         1      1      0      1  1386
     2         1      1      0      1  2632
     3         1      1      0      1  615
     4         1      1      0      1  1968
     OK        1      1      0      1  0        (标定最低 0)

   **它还能回放历史日志**（不接板子也能用）：

   ```
   已用三份历史日志验证过：修复前那份 → 四个方向键正常、`OK 0 次` → 直接报

### 如果 OK 仍然没反应

看日志属于哪种情况，都是"照着填数"就能解决：

| 日志表现 | 含义 | 怎么办 |
|---|---|---|
| 按 OK 时完全没有任何 `[keyscan]` 变化行 | 线没接好 / OK 键本身没接通 | 查 IO10 接线，或用万用表量 OK 按下时 IO10 对 GND 是否导通 |
| 有变化但打出 `读数 NNNmV 落不进任何键档` | 该模块的分压值与本机不同 | 把日志里的 mV 填进 `adkey_logic.h` 的 `ADKEY_KEYn_MV`，或调整 `ADKEY_OK_LOW_MAX_MV` |

> **关于"高压残余档"（已实机证伪并默认关闭）**：`ADKEY_OK_MIN_MV = 2900` 那条高档
> 原是为兼容"OK 贴近 VCC"的其它批次模块。实机抓包证明在**本机键盘上它只有坏处**：
> 空闲时读数会无规律跌到 2905~3124mV（30~220mV 的噪声），而高档会把每一次跌落都
> 判成"按下 OK"，日志里每几秒就冒一串**只持续 30ms 的假 OK**，菜单会自己乱跳。
> 所以 [adkey_logic.h](../components/BSP/ADKEY/adkey_logic.h) 里 `ADKEY_OK_HIGH_ENABLE`
> **默认置 0（关闭）**；单测里有 7 条实机噪声回归用例（2905~3124mV 必须判成"无按键"）。
> 换成"OK 不在 0mV"的模块时才置 1。
>
> 空闲读数仍有 30~50mV 的偶发跌落（约每 20~30 秒一次），现在会被正确忽略 —— **既不产生按键事件，
> 也不再打那条 `读数 NNNmV 落不进任何键档` 告警**（告警已收窄到只报"低于最高方向键档"的读数，
> 见第 3 节第 4 条）。所以正常待机时串口应当是**完全安静**的；一旦看到那条告警，才说明
> 真有一个本机没标定过的档位被按下了。

## 5c. 顺带修掉的第二个真问题：ADC 被两个任务抢锁 → 整批采样失败

键盘接进来之后，ADC1 变成**两个任务共用**：

| 任务 | 频率 | 通道 |
|---|---|---|
| 五位键盘（ADKEY） | 每 10ms 读一次，每次 4 个采样（≈400 次/秒） | CH9 / IO10 |
| 传感器（光敏 + 雨滴） | 每 1000ms 读一次，每次 16 个采样 | CH0 / CH1 |

实机日志里出现了大量**整批失败**：

```text
E ADC_BUS: all 4 samples failed on channel 9       ← 键盘侧，90 秒里 11 次
E ADC_BUS: all 16 samples failed on channel 0      ← 光照侧，90 秒里 2 次
W SENSOR: 光照 ADC 读取失败，light_mv 保留上次值
```

**根因在 IDF 驱动里**（`$IDF_PATH/components/esp_adc/adc_oneshot.c`）：它用的是**非阻塞 try-lock**：

```c
if (adc_lock_try_acquire(handle->unit_id) != ESP_OK) {
    return ESP_ERR_TIMEOUT;        // 拿不到锁立刻失败，不等待
}
...
return valid ? ESP_OK : ESP_ERR_TIMEOUT;
```

两个任务撞上时，抢输的一方**整批采样全部超时失败**；而 100Hz 的键盘任务会把
16 连采的传感器饿死（livelock）。这也正是我们在旧固件里抓到过的那次
`LoadProhibited` panic 的同一段代码路径。

**修法**（[`components/BSP/ADC/adc_bus.c`](../components/BSP/ADC/adc_bus.c)）：
在 adc_bus 这一层用**自己的递归互斥锁**把所有 ADC 访问串行化，让 IDF 那把 try-lock
永不产生竞争；再加 3 次重试兜底，并把真实错误码以 5 秒限速打出来（以前只统计次数，
看不出是 `ESP_ERR_TIMEOUT`）。

**实机验证**：修复前 90 秒 13 次整批失败 → 修复后 **0 次**（`logs/adkey-live3.log`）。

### 为什么构建镜像不放在项目里？

因为本工程源码路径含中文（`esp32智能家居_客户`），IDF 在 Windows 上会**连环报错**
（kconfig 的 `FileNotFoundError` / ccache 的 `Cannot convert character sequence` / ldgen 的
`libxtensa.a: No such file or directory`，详见 [README 第 12 节](../README.md)）。
唯一可靠解法就是把源码**镜像到纯 ASCII 目录**再编译，所以镜像必须放在项目外。
（沙箱里的 Python 环境放在中文路径下没问题 —— 实测通过；出问题的是被传给原生工具的那条**源码路径**。）

> 小贴士：如果你把整个工程移到纯 ASCII 路径（例如 `C:\esp32_smart_home`），
> 连镜像都不需要了，脚本会自动在原地编译。

### 这套环境踩过的 6 个坑（都已修在脚本里，别再改回去）

|:-:|------|------------|
| 1 | `The string is missing the terminator` + 中文变乱码 | 本机 shell 是 **Windows PowerShell 5.1**，`.ps1` 没有 UTF-8 BOM 时按 GBK 解码。**带中文的 ps1 必须存成 UTF-8 带 BOM**（`run_idf.ps1` 每次会自动补 BOM，所以永远走它） |
| 2 | `espidf.constraints.v5.4.txt doesn't exist` | 没跑过官方 install 脚本 → 设 `IDF_PYTHON_CHECK_CONSTRAINTS=no`（IDF 官方 Dockerfile 同款做法） |
| 3 | `Version.coerce(None)` TypeError | 缺 `ESP_IDF_VERSION`（正常由 export 脚本写）→ 手工设为 `5.4` |
| 4 | `"cmake" must be available on the PATH` | ★ PowerShell 里 `,` 优先级**高于** `+`：`@($PyEnv + '\Scripts', $a, $b)` 被解析成 `$PyEnv + ('\Scripts',$a,$b)`，字符串与数组相加按空格拼接 → 整条 PATH 变成一段。必须逐项 `Join-Path` 后用 `-join ';'` |
| 5 | `--interface_version: invalid choice: 3 (choose from 4,5,6)` | pip 装到的 `idf-component-manager` 太新，与 IDF 5.4.0 的 cmake 不兼容 → 设 `IDF_COMPONENT_MANAGER=0`（本工程无远程组件依赖，`dependencies.lock` 里只有 idf 本身） |
| 6 | `UnicodeDecodeError: 'gbk' codec can't decode byte 0x80`（读 sdkconfig） | sdkconfig 里有中文 SSID（UTF-8）→ 设 `PYTHONUTF8=1` |
| 7 | `'...\penv\python.exe' is currently active … was configured with '<旧路径>'` | 换过 Python 环境位置后，旧 build 缓存里的路径对不上 → 跑一次 `-Task fullclean,build` 即可 |
| 8 | 脚本一行输出都没有，直接报 `Cannot bind argument to parameter 'Path' because it is null` | **我自己把中文注释写进了本该纯 ASCII 的 `run_adkey_test.ps1`**，没有 BOM → PS 5.1 按 GBK 解码把脚本解析坏了。**纯 ASCII 脚本要一直保持纯 ASCII**（要么就带 BOM） |
| 9 | MinGW gcc `rc=1` 且**一句诊断都不打** | MSYS2 的 gcc 要靠 PATH 找 `cc1.exe`/`as`/`ld`，只给绝对路径不行 → 先把 `C:\msys64\mingw64\bin` 加进 PATH |
| 10 | gcc 报找不到源文件（路径含中文） | MinGW 工具链对含中文的路径抓瞎 → 把被测源码/头文件拷到 `%TEMP%\adkey_test_build` 这种纯 ASCII 暂存目录再编译 |

> 顺带一提：IDF 5.4.0 与工程原来的 5.4.4 编译结果兼容，编译**零 error**（只有 astra_ui 里两处
> `defined but not used` 的静态函数 warning，与本次改动无关）。
